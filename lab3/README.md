## Запуск

Нужны Docker с Compose и [uv](https://docs.astral.sh/uv/).
Из корня репозитория:

```bash
git switch lab-03
docker compose up -d --wait
cd lab3
uv sync --locked
uv run python -m scripts.create_schema
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Python 3.13 указан в `.python-version`. PostgreSQL 16 запускается
из `../compose.yaml` на `127.0.0.1:5433`. Данные лежат в Docker volume.
Скрипт создания схемы запускается до приложения; существующие таблицы сохраняет.
Swagger: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).
Сначала создайте категорию, затем товар с её UUID, затем отзыв с UUID товара.

После изменения моделей таблицы можно пересоздать. Эта команда удаляет данные
трёх таблиц учебного каталога:

```bash
uv run python -m scripts.create_schema --recreate
```

Приложение останавливается через Ctrl+C. База — командой
`docker compose down` из корня репозитория; volume при этом сохраняется.

## Конфигурация

Настройки читаются из переменных окружения или `lab3/.env`.
При необходимости скопируйте `cp .env.example .env`. Переменные окружения
имеют приоритет. В репозиторий включён только `.env.example`.

| Переменная | По умолчанию | Значение |
|---|---|---|
| `STORAGE_BACKEND` | `database` | Только `memory` или `database` |
| `DATABASE_URL` | `postgresql+asyncpg://catalog:catalog@127.0.0.1:5433/catalog` | Адрес учебного PostgreSQL с драйвером asyncpg |
| `SQL_ECHO` | `false` | Булево значение; `true` выводит SQL |
| `MAX_PRODUCT_STOCK` | `1000` | Целое от 1 до 1 000 000 включительно |

Пароль `catalog` относится только к локальной учебной базе из Compose.
Настройки проверяются при загрузке приложения. Неверный лимит или неизвестное
хранилище останавливают запуск с именем ошибочного поля.

Для работы в памяти база не нужна:

```bash
STORAGE_BACKEND=memory uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В этом режиме данные исчезают при перезапуске. Запускайте один worker:
память между процессами не разделяется. В режиме `database` данные сохраняются.

## Как устроен код

```text
app/routers/v1/       запрос, один вызов сценария, HTTP-ответ
app/use_cases/        правила и операции с категориями, товарами, отзывами
app/repositories/    Protocol, словари, реализация на AsyncSession
app/models/          внутренние модели — они же модели SQLAlchemy
app/schemas/         схемы запросов и ответов Pydantic
app/exceptions/      ошибки сценариев и единый формат ответа
app/dependencies/    сборка сценариев, выбор репозитория, выдача сессии
app/core/            настройки, движок и фабрика сессий
scripts/             создание схемы и демонстрации задач 6–8
```

Роутер не обращается к хранилищу. Репозиторий не проверяет правила бизнеса.
Сценарий получает репозитории и нужный лимит через конструктор.
Словари создаются один раз на процесс. Для PostgreSQL одна сессия и одна
транзакция выдаются на запрос через зависимость с `yield`.
Репозитории вызывают `flush`, зависимость фиксирует транзакцию либо откатывает её.
FastAPI закреплён в версии 0.115.14: завершение этой зависимости происходит
до отправки ответа клиенту.

## Правила каталога

1. У продавца не может быть двух товаров с одинаковым названием в одной категории.
   Название сравнивается точно, после удаления крайних пробелов входной схемой.
2. Остаток товара не должен превышать `MAX_PRODUCT_STOCK`.
3. Товар ссылается на существующую категорию, отзыв — на существующий товар.

Первые два правила собраны в `ProductService._check_rules` и вызываются при
создании и полной замене. При замене текущий UUID исключается из сравнения:
повторный PUT с теми же данными проходит. Отказ правила даёт `409`, неизвестная
ссылка — `404`, неверные поля запроса — `422`.

Идентификаторы — UUID, генерируются приложением. Вместо аутентификации
сохранена заглушка владельца `00000000-0000-0000-0000-000000000001` из lab2.
Внутреннее поле `created_at` нужно для порядка списков, в API оно не выдаётся.

## API и удаления

Пути и схемы второй работы сохранены: `/api/v1/categories`, `/api/v1/products`,
`/api/v1/reviews`. Для каждой сущности есть GET списка, POST, GET по UUID,
PUT и DELETE. PATCH есть у категорий и отзывов. POST возвращает `201` с
`Location`, DELETE — `204` без тела. Фильтры, сортировка и `limit`/`offset`
списка товаров сохранены. Полный контракт виден в Swagger.

| Связь | Удаление родителя | Настройка БД |
|---|---|---|
| Категория → товары | Запрещено, пока есть товары; ответ `409` | `ON DELETE RESTRICT` |
| Товар → отзывы | Отзывы удаляются вместе с товаром | `ON DELETE CASCADE` |

Категории нужны товарам, поэтому удалять занятую категорию нельзя.
Отзывы без товара не нужны, поэтому они удаляются вместе с ним.
Для категории `passive_deletes="all"` запрещает ORM обнулять ссылки.
Для отзывов `cascade="all, delete-orphan"` согласован с
`passive_deletes=True`: незагруженные отзывы удаляет PostgreSQL.
Словари повторяют то же поведение.

Ошибки сохраняют формат второй работы:

```json
{"error":{"code":"conflict","message":"Операция запрещена: объект связан с другими записями","details":[]}}
```

Ошибки правил содержат в `details` идентификатор или лимит.
Текст исключений PostgreSQL и имена ограничений клиенту не выдаются.

## Демонстрации и проверка

Из `lab3`, при запущенной базе и созданных таблицах:

```bash
uv run python -m scripts.sql_injection
uv run python -m scripts.cascade_delete --mode database
uv run python -m scripts.n_plus_one
uv run ruff check app scripts
uv run ruff format --check app scripts
```

Скрипты создают свои данные и в конце откатывают их транзакции.
`sql_injection` сравнивает небезопасный SQL, параметр `text()` и выражения ORM,
а затем показывает экранирование `%` и `_` в ILIKE.
`n_plus_one` выводит товары с названиями категорий четырьмя способами.
Его обычный доступ к незагруженной связи намеренно показывает `MissingGreenlet`.
